Two Repositories

ℹ️
Key Concept — Immutable vs Mutable Content:
In AEM Cloud Service, ui.apps and ui.config packages are immutable — deployed as a Docker image layer via Cloud Manager build. ui.content is mutable — installed as a content package after AEM starts. This distinction is critical for understanding deployment logs and troubleshooting.

5.2 — CORS Configuration (Author tier)

🛠️
This was broken in initial setup and has been fixed. The original config.author CORS had empty alloworigin and a wrong regex — Universal Editor could not connect to AEM Author. See Section 6 for details.
json ui.config/.../config.author/com.adobe.granite.cors.impl.CORSPolicyImpl~zendxp.cfg.json 
{
  "supportscredentials": true,                  // UE uses IMS Bearer tokens
  "supportedmethods": [
    "GET", "HEAD", "POST",
    "PUT", "DELETE", "PATCH", "OPTIONS"   // PUT/DELETE needed for UE content edits
  ],
  "alloworigin": [
    "https://experience.adobe.com",               // Universal Editor host
    "https://main--dxp-ai-ue-eds--satishsapate.aem.page",
    "https://main--dxp-ai-ue-eds--satishsapate.aem.live"
  ],
  "alloworiginregexp": [
    "https://.*\\.aem\\.page",                     // All EDS preview branches
    "https://.*\\.aem\\.live",                     // All EDS live branches
    "https://.*\\.hlx\\.page",
    "https://.*\\.hlx\\.live"
  ],
  "supportedheaders": [
    "Origin", "Accept", "X-Requested-With",
    "Content-Type", "Access-Control-Request-Method",
    "Access-Control-Request-Headers",
    "Authorization",                             // IMS Bearer token header
    "CSRF-Token"
  ],
  "allowedpaths": [".*"],
  "maxage:Integer": 1800
}
⚠️
New project? When creating a new project, copy this CORS config exactly, replacing only the alloworigin EDS URLs with your project's URLs (main--{repo}--{owner}.aem.page).

Section 6

CORS Fix — Before & After

❌ Before (Broken)
  • supportscredentials: false
  • supportedmethods: [GET, HEAD, POST]
  • alloworigin: [] (empty)
  • alloworiginregexp: [wrong regex]
  • supportedheaders: [basic only]
  • No Authorization header
✅ After (Fixed)
  • supportscredentials: true
  • + PUT, DELETE, PATCH, OPTIONS
  • alloworigin: experience.adobe.com + EDS hosts
  • alloworiginregexp: *.aem.page / *.aem.live
  • + Authorization header
  • + CSRF-Token header

Why each change was needed

PropertyReason for change
supportscredentials: trueUniversal Editor uses IMS OAuth Bearer tokens. When Authorization header is included in a CORS request, the browser requires Access-Control-Allow-Credentials: true. With false, UE operations silently fail.
alloworigin: experience.adobe.comUniversal Editor runs at experience.adobe.com. It makes fetch requests to AEM Author. Without this origin, all UE → AEM API calls are blocked by CORS.
alloworiginregexp: *.aem.pageEDS previews use dynamic URLs like branch--repo--owner.aem.page. Regex covers all branches/PRs automatically.
PUT, DELETE, PATCH, OPTIONSUniversal Editor performs content CRUD. Edit = PUT, Delete component = DELETE. Without these methods, editing is read-only.
Authorization headerIMS tokens are sent in the Authorization: Bearer ... header. Must be in supportedheaders or the preflight OPTIONS request fails.

Section 9

fstab.yaml — AEM Mountpoint

✅
Current fstab.yaml is correctly configured and verified.
yamlfstab.yaml (in EDS GitHub repo root)
mountpoints:
  /: # Single root mount — all pages come from AEM via Franklin Delivery Servlet
    url: https://author-p24056-e1593080.adobeaemcloud.com/bin/franklin.delivery/satishsapate/dxp-ai-ue-eds/main
🚨
CRITICAL: The URL must include the /bin/franklin.delivery/{owner}/{repo}/{ref} path. A bare AEM author URL (https://author-xxx.adobeaemcloud.com) will NOT work — EDS cannot fetch AEM content without the Franklin Delivery Servlet path. This is the most common setup mistake.
✅ Correct Pattern (XWalk)

Single / mountpoint pointing to AEM Author via Franklin Delivery Servlet path /bin/franklin.delivery/{owner}/{repo}/{ref}. EDS fetches all page content from AEM JCR through this endpoint which converts JCR content to EDS format.

❌ Wrong Pattern (avoid)

Bare AEM URL without servlet path, or multiple mountpoints pointing to localhost. The Franklin Delivery Servlet path is mandatory for EDS to read AEM content.

yamlTemplate for new projects
mountpoints:
  /:
    url: https://author-p{programId}-e{environmentId}.adobeaemcloud.com/bin/franklin.delivery/{githubOwner}/{repoName}/{branch}

# Example:
# url: https://author-p24056-e1593080.adobeaemcloud.com/bin/franklin.delivery/satishsapate/dxp-ai-ue-eds/main

# NEVER use:
# url: https://author-p24056-e1593080.adobeaemcloud.com        ← bare URL, missing servlet path
# url: http://localhost:4502                                   ← localhost not reachable by EDS
⚠️
Where does the Franklin Delivery Servlet come from? The servlet (/bin/franklin.delivery) is provided by the FranklinRepositoryImpl OSGi configuration deployed in your AEM Cloud instance via Cloud Manager. It translates AEM JCR pages into the format EDS expects. The {owner}/{repo}/{ref} segment must match your FranklinRepositoryImpl config (owner, repo, ref properties).

head.html — Universal Editor Connection

✅
Current head.html is correctly configured with the UE connection meta tag.
htmlhead.html (in EDS GitHub repo root)
<meta
  http-equiv="Content-Security-Policy"
  content="script-src 'nonce-aem' 'strict-dynamic' 'unsafe-inline' http: https:; base-uri 'self'; object-src 'none';"
  move-to-http-header="true"
>
<meta name="viewport" content="width=device-width, initial-scale=1"/>

<!-- CRITICAL: Tells Universal Editor which AEM instance to connect to -->
<meta name="urn:auecon:aemconnection"
      content="aem:https://author-p24056-e1593080.adobeaemcloud.com"/>

<script nonce="aem" src="/scripts/aem.js" type="module"></script>
<script nonce="aem" src="/scripts/scripts.js" type="module"></script>
<link rel="stylesheet" href="/styles/styles.css"/>

The urn:auecon:aemconnection meta tag is the bridge between EDS pages and Universal Editor. Format: aem:{authorUrl}. Universal Editor reads this when opening a page to know which AEM instance to communicate with.

Section 15

Known Issues & Resolutions

All issues encountered and resolved during the initial project setup. Reference these before opening a support ticket.

Expected Behavior /apps/zendxp/osgiconfig path returns "Resource not found"
Symptom

Browsing https://author-p24056-e1593080.adobeaemcloud.com/apps/zendxp/osgiconfig/config.tidy.json returns: "Resource at '/apps/zendxp/osgiconfig/config.tidy.json' not found"

Root Cause

AEM Cloud Service has built-in security filters that block HTTP access to /apps/*/osgiconfig/** paths. The JCR nodes exist in the immutable repository but cannot be accessed via browser URL. This is intentional — OSGi configs may contain sensitive data.

Resolution

This is not a bug. Use Cloud Manager Developer Console → OSGi → Configurations to verify configs. Never try to browse osgiconfig paths via HTTP in AEM Cloud.

Expected Behavior /system/console/configMgr returns 404
Symptom

Trying to access Felix Web Console at /system/console returns 404 or redirect.

Root Cause

Felix Web Console is completely disabled in AEM as a Cloud Service for security. This is by Adobe design — you cannot access it at all via the author URL, unlike AEM 6.5.

Resolution

Use the Cloud Manager Developer Console instead (accessible only via Cloud Manager UI after login). It provides OSGi config inspection, bundle status, Sling config, and more.

Resolved Universal Editor cannot connect to AEM Author — CORS errors
Symptom

Opening a page in Universal Editor fails. Browser console shows CORS errors. UE editor panel does not load component properties.

Root Cause

The config.author/CORSPolicyImpl~zendxp.cfg.json had: (1) empty alloworigin, (2) wrong alloworiginregexp pattern, (3) missing supportscredentials: true, (4) missing PUT/DELETE/PATCH methods, (5) missing Authorization header. The config.author run mode overrides the general config on author tier, so the general CORS with alloworigin: ["*"] never applied on author.

Fix Applied

Updated config.author/CORSPolicyImpl~zendxp.cfg.json with correct UE origins, methods, and headers. See Section 6 for full before/after comparison.

File Changed

zendxp/ui.config/src/main/content/jcr_root/apps/zendxp/osgiconfig/config.author/com.adobe.granite.cors.impl.CORSPolicyImpl~zendxp.cfg.json

Resolved fstab.yaml — two separate fixes required (commits a316d72 + ea8005d)
Fix 1 — Multiple localhost mountpoints (commit a316d72)

Original file had 3 mountpoints (/, /content, /conf) all pointing to localhost:4502. EDS CDN cannot reach localhost. Simplified to single / root mount pointing to AEM Cloud URL.

Fix 2 — Missing Franklin Delivery Servlet path (commit ea8005d) — CRITICAL

After Fix 1, the URL was still a bare AEM author URL (https://author-xxx.adobeaemcloud.com) without the servlet path. EDS cannot read AEM JCR content without the Franklin Delivery Servlet endpoint. This was identified via Adobe Support as the root cause of the code: 400 EDS error.

yaml
# ❌ After Fix 1 — bare URL, still wrong
mountpoints:
  /:
    url: https://author-p24056-e1593080.adobeaemcloud.com

# ✅ After Fix 2 — correct with franklin.delivery servlet path
mountpoints:
  /:
    url: https://author-p24056-e1593080.adobeaemcloud.com/bin/franklin.delivery/satishsapate/dxp-ai-ue-eds/main
Why the Servlet Path is Mandatory

The /bin/franklin.delivery/{owner}/{repo}/{ref} endpoint is the FranklinRepositoryImpl OSGi servlet deployed in AEM Cloud. It translates JCR content into the markdown/HTML format that EDS expects. Without it, the URL returns raw AEM HTML (or a login page), not the content EDS can index.

Resolved EDS Admin API returns "code": {"status": 400} — code bus not activated
Symptom

Checking https://admin.hlx.page/status/satishsapate/dxp-ai-ue-eds/main returned "code": {"status": 400}. Files like /scripts/aem.js returned 404 from main--dxp-ai-ue-eds--satishsapate.aem.page. No GitHub webhook appeared in the repo settings after installing AEM Code Sync App.

Root Cause

The EDS code bus was not activated for this GitHub repository because the original fstab.yaml used a bare AEM author URL (without the Franklin Delivery Servlet path), causing EDS validation to fail at install time. Additionally, the AEM Code Sync GitHub App webhook was not auto-created.

Resolution (Adobe Support + Manual Fix)
  • Raised Adobe Support ticket — Adobe engineering confirmed the code bus activation issue
  • Fixed fstab.yaml to use the Franklin Delivery Servlet URL (commit ea8005d) — this was the root cause
  • Re-installed AEM Code Sync GitHub App on the repository after the fstab fix
  • Triggered manual code bus activation via POST https://admin.hlx.page/code/satishsapate/dxp-ai-ue-eds/main
  • Verified: https://admin.hlx.page/status/satishsapate/dxp-ai-ue-eds/main now returns "code": {"status": 200}
  • Verified: https://main--dxp-ai-ue-eds--satishsapate.aem.page/scripts/aem.js returns the file correctly
Key Lesson

Always ensure fstab.yaml is correct with the Franklin Delivery Servlet URL before installing the AEM Code Sync App. If you install the app with a broken fstab, EDS may fail to activate the code bus. Fix the fstab first, then reinstall the app and trigger a manual sync.

Expected Behavior Deploy step log shows no ui.config installation
Symptom

Reviewing Cloud Manager deploy step log shows only zendxp.ui.content being installed. No mention of ui.config or ui.apps.

Root Cause

The deploy step log only captures mutable content installation (job: aem-install-mutable-content). The ui.config and ui.apps packages are immutable — they're baked into the Docker container image during the build step. They do not appear in the deploy step log.

How to Confirm Immutable Content Deployed

Look in the deploy log for evidence of OSGi service registrations, e.g. CORSPolicyImpl~zendxp ServiceEvent REGISTERED. If the service registers, the config deployed successfully. Verify configs in Developer Console.

Root Cause

Fix Applied

  • Google Fonts: Sora (headings) + DM Sans (body) via @import

  • Shape/shadow tokens: --radius-sm/md/lg/xl, --shadow-glow
  • Buttons: pill-shaped (border-radius: 999px), purple gradient background
  • --nav-height: 72px, section max-width: 1280px, margin: 0
Resolved Header block did not match html-kit design — content structure mismatch
Symptom

The header rendered as a plain nav using the EDS fragment approach (loading /nav page content). This could never produce the rich DXP AI header structure (gradient logo text, dropdown panels with icons and descriptions, styled CTA buttons).

Root Cause

The original header.js used EDS's default fragment-loading pattern, mapping sections from the /nav page (brand/sections/tools). This inherently limits the header to plain link lists.

Fix Applied (commit c88d41e)

Complete rewrite of header.js to render the full DXP AI navigation HTML directly (bypassing the fragment approach). Features:

  • Logo: "DXP AI" with gradient text + "Powered by ZensAI" sub-label
  • Desktop nav: Platform dropdown (4 items with icon+title+desc), Solutions, Why DXP AI, Resources dropdown (3 items), Pricing, About
  • Action buttons: ghost "Login" + gradient "Request Demo"
  • Hamburger → .nav-mobile-menu slide-down with full link list

Resolved Windows: pre-commit hook "Exec format error" — Husky file encoding issue
Symptom

On Windows, running git commit triggered a Husky pre-commit hook that failed with hint: The '.husky/pre-commit' hook was ignored because it's not set as executable. Exec format error.

Root Cause

The .husky/pre-commit file was missing the #!/bin/sh shebang line and had CRLF line endings (Windows default). Without the shebang, the shell could not determine how to execute the script.

Fix Applied

Added #!/bin/sh as the first line of .husky/pre-commit and ensured LF line endings (commit 07c626d). For new Windows developers:

bash
# Prevent CRLF conversion on clone
git config core.autocrlf false

# If already cloned and hook fails:
sed -i 's/\r//' .husky/pre-commit
# Ensure first line is: #!/bin/sh
